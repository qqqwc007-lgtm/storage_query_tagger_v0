## What Makes This Cool

这个看板不是“收纳标签统计表”，而是一个把长尾搜索词压成机会簇的机器。

它应该让人从一堆词，直接走到一句能开会讨论的话：

`这个场景下，用户最强的需求是什么，最适合什么形态，为什么值得看。`

## Constraints

- 不能把 [选品评估表v2.xlsx](/Users/wayneqqq/Desktop/选品评估表v2.xlsx) 的字段当成现成 schema 直接套用，它只是结构参考，不是语义参考。

- 第一版要快，最好落在 Excel 里，但不能把所有逻辑都埋进透视表黑箱。
- 当前不做 `组合供应链`、`综合评分`、`竞品市场情况` 自动化。
- 所有可见 sheet 都应读取 interface tables，而不是直接吃原始 CSV。
- 这份文档只定义方案，不启动实现。

## Premises

1. 这个项目的目标是把 `kw.csv` 变成“决策视图”，不是做打标 QA。
2. 决策视图的基本单元不是单个标签，也不是单个关键词，而是 **机会簇**。
3. 机会簇的 **业务主键** 应是：`场景 × 需求 × 形态`。
4. `存储对象`、`使用场地`、`代表关键词` 默认是解释属性，不直接改变业务主键。
5. 第一版实现应选 `Approach A`，也就是 Excel-first，但输出的中间表必须是稳定 contract，方便未来切到 `Approach B`。
6. 主分析样本应以 `mapped + partial` 为主，`ambiguous` 单独进观察池，不混进核心排名。
7. 热度必须拆成多维指标，不能只看 raw count。
8. 业务逻辑必须显式写成规则表或汇总表，不能只存在人脑里。

## The Core Business Logic

### 决策单元

本项目选择的业务决策单元是：

`机会簇 = 场景 roll-up × 需求 roll-up × 形态 roll-up`

这不是标签桶，也不是直接产品名。它是中间那层“可决策的业务单元”。

例子：

- `卫浴 × 分类整理 × 盒类`
- `衣橱 × 竖向增容 × 架类`
- `厨房/Pantry × 密封防护 × 盒类`

这一层成立以后，才有资格继续往下长成候选产品方向。

### 为什么不是别的

如果只看标签桶，最后得到的是“bathroom 很热，container 很热”。这只是在描述数据。

如果直接跳到产品名，第一版会过度主观。你会得到很多像“也许可以做浴室收纳柜”的拍脑袋结论。

机会簇是中间那层。够抽象，能稳定聚合。也够具体，能拿去讨论。

对业务讨论来说，这就是最终语言。

但对实际落地来说，技术主键还要更稳一点。

### 技术主键

建议技术上使用一个更稳的语义 key：

`cluster_key = {cluster_key_version, anchor_type, anchor_value, object_key, form_rollup_key, function_key}`

解释：

- `anchor_type / anchor_value` 是簇的锚点
- 理想情况锚点来自 `scene`
- 如果 `scene` 缺失，再按 `place -> object -> function` 回退
- `marketplace`、`date`、`taxonomy_version` 作为切片字段，不进业务主键
- `material`、`size`、`form_specific_set` 作为解释属性，不在 v1 中切簇

这层设计的意义是：

- 对业务，还是讲 `场景 × 需求 × 形态`
- 对实现，不会因为缺一个 scene 就完全掉出体系
- `object_key` 只服务于技术去冲突，不改变 dashboard 上展示的业务粒度

### 机会簇结构

建议第一版每个机会簇至少输出这些字段：

- `cluster_id`
- `scene_rollup`
- `need_rollup`
- `form_rollup`
- `primary_object`
- `secondary_objects`
- `primary_location`
- `keyword_count`
- `top100k_count`
- `rank_weight_score`
- `object_concentration`
- `priority_score`
- `example_keywords`
- `source_row_count`
- `completion_rate`
- `notes`

建议字段再补 4 个技术辅助列：

- `anchor_type`
- `anchor_value`
- `cluster_quality`
- `partial_share`

其中：

- `scene_rollup / need_rollup / form_rollup` 是主键
- `primary_object` 是解释“这类需求主要在收什么”
- `primary_location` 是解释“这类需求主要发生在哪”
- `completion_rate` 用来判断这个簇是不是逻辑完整，而不是一堆残缺标签拼出来的
- `cluster_quality` 用来区分正式簇和候选簇
- `partial_share` 用来给“信息不完整”的簇做降权

## Transformation Logic

### 1. 输入层

主分析池：

- 只纳入 `mapping_status in ('mapped', 'partial')`

观察池：

- `mapping_status = ambiguous`

排除池：

- `mapping_status = not_storage`

### 2. 场景 roll-up

`scene_rollup` 的推导优先级：

1. `产品使用场景`
2. `产品使用场地`
3. `存储对象`

建议第一版场景桶：

- 衣橱 / 卧室
- 卫浴
- 厨房 / Pantry
- 儿童房 / 玩具
- 起居室 / 玄关 / Home Office
- 车库 / 工具间
- 床底 / 换季 / 季节性
- 美妆 / 珠宝 / 小件
- 食品 / 宠物密封
- 其他收纳

同时建议技术上定义：

- 如果 `产品使用场景` 非空，`anchor_type = scene`
- 如果 `scene` 为空但 `产品使用场地` 非空，`anchor_type = place`
- 如果 `scene/place` 都空但 `存储对象` 非空，`anchor_type = object`
- 如果前三者都空但 `产品功能` 非空，`anchor_type = function`

示例：

- `shoe storage`, `closet organization`, `closet` -> `衣橱 / 卧室`
- `bathroom organization`, `bathroom`, `over toilet`, `under sink` -> `卫浴`
- `food storage`, `pantry organization`, `kitchen`, `spice organization` -> `厨房 / Pantry`

### 3. 需求 roll-up

`need_rollup` 不直接等于 `产品功能`。它要由多个字段联合推导。

建议第一版需求桶：

- 分类整理
- 竖向增容
- 封闭收纳
- 陈列展示
- 压缩收纳
- 安装 / 移动
- 密封防护

推导优先级：

1. `产品功能`
2. `产品形态关键词`
3. `产品使用场景`

映射原则：

- `drawer organizer`, `caddy`, `divider` -> `分类整理`
- `rack`, `shelf`, `cabinet organizer`, `tier` -> `竖向增容`
- `bin`, `box`, `bag`, `container`, `cabinet` -> `封闭收纳`
- `display` -> `陈列展示`
- `vacuum`, `collapsible`, `foldable` -> `压缩收纳`
- `rolling`, `wheeled`, `wall mounted`, `hanging` -> `安装 / 移动`
- `with lid`, `airtight`, `waterproof`, `lockable` -> `密封防护`

### 4. 形态 roll-up

`form_rollup` 的目标不是保留所有 taxonomy 细颗粒度，而是稳定归到可决策的产品家族。

建议第一版形态桶：

- 柜类
- 架类
- 盒类
- 箱 / bin 类
- 袋类
- 篮 / basket 类
- 整理器类
- 抽屉整理类
- 台车类
- 展示类
- 其他形态

映射原则：

- `cabinet`, `storage cabinet` -> `柜类`
- `rack`, `shelf`, `display shelf` -> `架类` 或 `展示类`
- `box`, `container`, `storage container` -> `盒类`
- `bin`, `storage bin` -> `箱 / bin 类`
- `bag` -> `袋类`
- `basket` -> `篮 / basket 类`
- `organizer` 类泛词 -> `整理器类`
- `drawer organizer` -> `抽屉整理类`
- `cart` -> `台车类`

第一版先做“先归一，再选主类”：

- `["storage cabinet", "cabinet"]` -> `柜类`
- `["storage bin", "bin"]` -> `箱 / bin 类`
- `["storage container", "container"]` -> `盒类`

不要让父子同义词把同一个 query 拆成两个簇。

### 5. 对象与场地

`存储对象` 和 `产品使用场地` 不进入主键，但要作为解释层补上：

- `primary_object` = 该簇内出现频次最高的对象
- `secondary_objects` = 频次前 2-3 的其余对象
- `primary_location` = 该簇内出现频次最高的场地

这样做的原因是，第一版先确保簇稳定，再用对象解释簇，不反过来让主键爆炸。

## Ranking Logic

### V1 基础指标

每个机会簇输出三类基础热度指标：

- `keyword_count`
- `top100k_count`
- `rank_weight_score = Σ(1 / search_frequency_rank)`

解释：

- `keyword_count` 看覆盖广度
- `top100k_count` 看高热关键词渗透
- `rank_weight_score` 看头部热度权重

### V1 聚焦指标

第一版建议再加两个“不是所有热词都值得做”的校准指标：

- `completion_rate`
  公式：簇内成功解析出 `场景 + 需求 + 形态` 三要素的行数 / 簇内总行数
- `object_concentration`
  公式：簇内 `primary_object` 的占比

### V1 机会分

第一版建议用一个更直接、更可落地的线性公式：

`priority_score = 100 * (0.45 * PERCENTRANK(rank_weight_score) + 0.35 * PERCENTRANK(top100k_count) + 0.20 * PERCENTRANK(keyword_count)) * specificity_factor(anchor_type) * (1 - 0.25 * partial_share)`

定义补全：

- `PERCENTRANK(x)` = 在 **同一批次、同一 marketplace、同一 date 的 eligible clusters** 中按升序做 Excel `PERCENTRANK.INC`
- 若出现并列，使用 Excel 默认并列百分位
- `eligible cluster` 必须满足：
  - `keyword_count >= 5`
  - `top100k_count >= 1`
  - `completion_rate >= 0.50` 或 `cluster_quality = candidate`
- 不满足条件的簇不参与 Top ranking，只能进 backlog 或 watchlist

推荐的 `specificity_factor`：

- `scene = 1.00`
- `place = 0.85`
- `object = 0.75`
- `function = 0.60`
- `form only = 0.35`

理由：

- `scene` 驱动的簇通常最可行动
- 泛 form 簇很多，但可决策性弱，必须降权
- `partial_share` 让“信息残缺但热”的簇不会轻易冲到前面
- 这个公式在 Excel 里好解释，也能直接做

### State Model

为了避免 `candidate / backlog / watchlist / 待成簇池` 混用，v1 统一成三层状态：

#### 行级结果 `row_outcome`

- `main_pool`
- `candidate_pool`
- `watchlist`
- `drop`

#### 簇级结果 `cluster_quality`

- `ready`
- `candidate`
- `backlog`

#### 页面去向

- `ready`：可进入 `00_Overview`、`01_Opportunity_Cluster_Matrix`、`02_Cluster_Drilldown`
- `candidate`：只进 `02_Cluster_Drilldown`
- `backlog`：只在 `03_Methodology_And_Definitions` 记录规则口径，不进 Top list
- `watchlist`：不生成正式簇，只保留在观察池导出

明确规则：

- **Top 10 只允许 `ready` 簇出现**
- `candidate` 可以保留，但不能混入总览排名

## Fallback Rules

### partial 行

`partial` 行进入主分析池，但有条件：

- 如果能补出 `场景 + 需求 + 形态`，则进入正式机会簇
- 如果缺任一主键字段，进入 `待成簇池`
- 如果只剩 `form`、`place` 或 `function` 这种弱锚点，则默认进 backlog
- 只有当它满足 `keyword_count >= 10` 且 `top100k_count >= 2` 时，才允许提升到候选簇

映射到状态：

- 满足完整三要素 -> `row_outcome = main_pool`
- 不完整但有明显业务方向 -> `row_outcome = candidate_pool`
- 只有弱锚点 -> `row_outcome = watchlist`

### ambiguous 行

`ambiguous` 不进主排名，只进观察池：

- 可按相近 `object / form / scene cue` 做“候选归属”
- 但只能在观察 sheet 里展示，不能并入机会分
- 不允许悄悄漏进主簇

### 多值字段

对数组字段，第一版不做复杂分摊，先做 **先归一、再选主类**：

- 先把同义或上下位词归到同一个 `form_rollup`
- 如果仍有多个不同主类，按更具体的形态优先

例子：

- `["storage cabinet", "cabinet"]` -> `柜类`
- `["storage bin", "bin"]` -> `箱 / bin 类`

### 无对象但有场景

允许成簇。

因为有些方向天然是按场景买，不是按对象买。比如：

- `bathroom storage cabinet`
- `under sink organizer`

### 无场景但有对象和形态

允许进入 `其他收纳` 场景桶，但优先级降低。

因为这种词通常更泛，适合看，不适合马上做决策。

## Concrete Cluster Examples

基于当前 `kw.csv` 已观测到的数据，第一版至少会稳定长出这些机会簇：

### 1. 衣橱 / 卧室 × 竖向增容 × 架类

- `shoe rack`
- `shoe rack for closet`
- `shoe rack for entryway`

- `primary_object = shoe`

代表来源：

- `pill organizer`
- `travel pill organizer`
- `weekly pill organizer`

解释属性：

## Worked Example

1. 原始行

   `产品使用场景 = shoe storage`
   `产品形态关键词 = ["rack"]`
   `存储对象 = shoe`
   `产品使用场地 = closet`

   `scene_rollup = 衣橱 / 卧室`
   `need_rollup = 竖向增容`
   `form_rollup = 架类`
   `anchor_type = scene`
   `primary_object = shoe`

   `keyword_count`
   `top100k_count`
   `rank_weight_score`
   `partial_share`
   最终得到 `priority_score`

这就是一条 raw query 变成业务机会簇的完整路径。
